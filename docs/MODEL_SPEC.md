# SolarCast 최종 모델 및 연동 명세

목표는 요청 구역의 최신 이용 가능 항공사진에서 **옥상과 설치 제약을 분할하고, 기존 태양광 패널을 별도 검출**해 설치 후보 면적과 연간 발전 잠재량을 계산하는 것이다. 아래는 최종 연동 명세다. 저장소의 나주 연구 결과는 근거 자료이며, Task 1 웹이 이를 추론하거나 표시하지는 않는다.

| 공개 저장소에 원본 제공 | 원본 JPEG와 `data/bitgaram/`은 공개 저장소 및 제출 ZIP에 포함하지 않는다. 건물 정보와 파생 산출물은 공개 조건을 확인한 후 포함 여부를 정한다. |

`data/bitgaram/`은 기존 연구용 자료이며 최종 서비스의 고정 입력이 아니다. 최종 서비스는 요청 구역의 영상과 건물 정보를 이용 조건을 확인한 뒤 조회해 분석한다. 학습·검증에는 별도로 이용이 허용된 영상과 라벨이 필요하며, 현재 저장소의 코드만으로 기존 자료 전체를 동일하게 재생성할 수는 없다. 데이터 준비 현황은 [안내](data/README.md)를 참고한다.

[브이월드 공식 이용약관 제13조·제19조](https://www.vworld.kr/v4po_prcint_a001.do)

**대표 샘플 확인:** `446765_207644.jpeg`는 수목과 길이 많이 보이는 256×256 타일이다. [과거 패널 탐지 출력](outputs/3_panels/panels_final.geojson)의 `PV_0001`은 이 타일을 참조하고 최고 신뢰도 약 0.527을 기록한다. 이 행은 예측 결과이지 패널 정답이 아니며, 수목·길 등과 혼동하는 오탐 후보는 수동으로 재검수한다. [옥상 산출물](outputs/2_roof/available_roof.geojson)의 건물 `1204317201`은 `valid=1`, 후보 조각 하나 `36.1㎡`; 건물 `1204317185`의 `806.9㎡` 후보 행은 `valid=0`으로 제외된다. 크기만으로 유효성을 판정할 수 없는 사례이며, 이 값은 현장 설치 검증값이 아니다. 추가 라벨셋에는 건물별 지붕·장애물 폴리곤, 패널이 없는 타일, 그늘·사선·시설물 혼동 사례 및 검수 상태를 포함한다.

## 2. 학습 과제와 모델

| 분기 | 학습 과제와 초기 구조 | 전처리 및 텐서 | 출력 |
|---|---|---|---|
| 옥상·장애물 | 지붕 및 장애물 2채널 의미 분할. 팀이 검수한 폴리곤에서 기존 SAM 보조 마스크를 수정하고, 경량 U-Net(사전학습 ResNet-18 인코더)으로 파인튜닝한다. 지붕과 지붕 위 장애물이 겹칠 수 있어 두 채널은 독립적으로 학습한다. | 건물 외곽을 여유 있는 RGB 크롭으로 만든 후 비율 유지 512×512 패딩, 0–1 스케일·인코더 정규화, NCHW `float32 [B,3,512,512]`. | 두 클래스 로짓 `float32 [B,2,512,512]`; sigmoid 및 검증 기준 임계값을 적용하고 패딩을 제거해 지붕/장애물 마스크 반환. |
| 기존 태양광 패널 | 인스턴스 세그멘테이션. [NLR RTMDet-Ins-X](https://github.com/NatLabRockies/Panel-Segmentation) 사전학습 체크포인트의 head를 태양광 단일 클래스로 바꾸고, 팀 라벨로 neck/head를 파인튜닝한다. 팀 연구 코드를 기준으로 검증한다. | 기본 RGB 256×256 타일을 비율 유지 640×640 패딩 후 NCHW `float32 [B,3,640,640]`. 모델 체크포인트 설정의 채널 순서·정규화와 지오메트리 변환을 고정한다. 큰 모자이크는 640 픽셀 창/96 픽셀 겹침부터 시험한다. | 타일별 가변 개수 N의 마스크 `[N,H,W]` (이진), 타일 픽셀 `xyxy [N,4]`, 클래스 `[N]`, 신뢰도 `[N]` (0–1). 중복은 겹침 구간에서 모아 제거한다. |

최종 제품의 주 분석은 옥상·장애물 모델과 별도 패널 모델을 모두 사용한다. 패널 모델의 입력·출력은 [기존 연구 코드](3_panel_detection/src/nlr.py)와 대조하며, 옥상 분기의 모델·라벨·품질 목표는 검증 대상이지 구현 완료가 아니다. 두 분기에서 원래 픽셀 → 크롭 → 모델 텐서 변환과 원복에 필요한 좌표 정보를 함께 기록한다.

## 3. 학습과 검증 계획

- 위치 누출을 막기 위해 같은 건물·인접하거나 겹치는 타일·유사 시점 복제 영상을 같은 그룹으로 묶어 train/val을 나눈다. 위 643/161 분할은 비교 기준일 뿐이다. 검증된 나주 외 권역을 학습·검증과 겹치지 않는 test로 별도 잠근다. 권역별 양성/음성, 시설 종류, 해상도, 촬영 시점, 주석 일치도를 확인한다.
- 옥상 라벨은 다음 단계의 작업이다. 이용 근거를 확인한 영상에서 **건물 40동을 1차 목표**로 잡는다. 4명이 10동씩 지붕 외곽과 옥상 장애물을 표시하고, 각 건물은 다른 팀원 1명이 원본과 대조한다. SAM 후보는 초안으로 쓴다. 옥탑·기계설비 등 고정 시설은 장애물에 표시하고, 그림자는 장애물에서 제외한다. 기존 패널은 장애물로 표시하지 않고 패널 모델이 따로 검출한다. 가림이나 위치 오차로 경계를 정하기 어려운 부분은 학습 손실에서 제외한다. 의견이 다른 마스크는 두 사람이 합의한 뒤 학습에 넣는다. 40동은 라벨링 절차와 소요 시간을 점검하기 위한 규모이며, 이미 확보한 수량이나 최종 학습 규모가 아니다.
- 옥상: 검수 라벨을 먼저 확보해 BCE+Dice 기준선을 학습하고 검증 IoU/Dice로 모델을 선택한다. 패널: 검증에서 `mAP@[.50:.95]`, AP50, precision, recall, 비패널 타일 오탐률로 체크포인트·신뢰도 임계값을 고른다. 두 모델 모두 회전·밝기·영상 품질 차이를 증강하고 타일 배경과 고층에서 실패 사례를 남긴다.
- 제품 검증: 수작업 후보 기준과 면적 MAE(㎡), 상대 오차, 기존 패널 중복 포함률을 권역별로 기록한다. 검증 데이터에서 산정 정책과 품질 게이트를 정한 뒤 독립 test에서 판정한다. 실제 계측이 없다면 발전량은 검증용 기준 계산기와 단위·공식 일치 여부만 확인하고 실측 정확도로 주장하지 않는다.

## 4. 설치 후보와 발전량 산정

1. 타일 인접 중복을 제거하고 마스크를 WGS84 GeoJSON(`longitude, latitude`)으로 변환한다. 건물과 매칭한 뒤 면적·거리 연산은 미터 단위 투영 좌표계로 수행한다.
2. 검출 지붕을 기준으로 건물 범위를 보정하고, 기존 패널·지붕 장애물·가장자리 및 통로 이격 구역을 제외한다. 작은 파편과 신뢰 불가 건물을 걸러내며 이격 거리·통로 기준은 설정과 출처를 기록한다. 구조 안전, 지붕 내하력·전기 연결 제약은 별도 검토가 필요하다.
3. 후보 다각형 안에 실제로 들어가는 모듈 수를 배치로 계산한다. 1.0×2.0 m, 400 W를 초깃값으로 사용한다. 후보 폴리곤 면적과 배치된 모듈 면적은 다르다.
4. 주변 건물까지 포함해 연간 일조율을 가중 표본화하고 70% 이상 배열만 집계한다. 용량(kW) = 유효 모듈 수 × 0.4. 발전량(kWh/년) = 각 유효 배열의 용량(kW) × 연 일사량(kWh/㎡/년) ÷ 기준일사강도(1 kW/㎡) × 일조율 × 성능계수 0.8의 합. 월 일사량이 일평균으로 제공되면 해당 월 일수를 곱해 연간 합산한다. 최종적으로 건물별 값과 구역 합계를 반환한다. 순간 음영 시각 변경은 연간 일사량을 바꾸지 않는다.

## 5. 시스템 구조와 인터페이스

```text
사용자 지도 선택 → Next.js 요청 중계 → 작업 큐 및 만료 저장소 ↔ Python 작업자
                                                          └─ 영상·건물 조회 → RGB 전처리 → 2개 모델 → 공간·일사량 산정
사용자 결과 화면 ← 상태/결과 조회 ← 작업 큐 및 만료 저장소
```

최종 계약이며 Task 1에는 이 주소들을 배포하거나 호출하지 않는다.

| 통로 | 페이로드·동작 |
|---|---|
| `POST /api/analysis` | `{ center: { longitude, latitude }, radiusM: 250\|500\|1000, shadowAt: ISO-8601 }`. 사용자가 제출한 것은 위치·반경·순간 음영 기준 시각이다. 입력 경계·지원 권역·타일 예산을 검증하고 `202 { jobId, status: 'queued' }`를 반환한다. 지원 밖/예산 초과는 설명과 함께 거절한다. |
| 영상 준비 → 모델 | 구역과 주변 음영 범위의 지리참조 RGB·건물 데이터. 출처·해상도·촬영일(없으면 null)·조회 시점과 처리한 영상 범위를 기록하고 요청과 모델 입력을 연결한다. 분석 영상은 지도 화면 캡처가 아니다. |
| `GET /api/analysis/{jobId}` | `{ status, stage, warnings, error?, result? }`. `status`: `queued`, `running`, `completed`, `failed`, `expired`; `stage`: `imagery`, `inference`, `estimation`. 실패 유형은 영상 없음, 권역 미지원, 불완전 데이터, 시간초과, 내부 오류를 구분한다. |
| 완료 결과 | 원본 요청 구역, 영상 메타데이터·모델 버전·적용 가정, `buildings`, `existingPanels`, `availableRoofs`, `shadows` GeoJSON. 패널에는 신뢰도, 설치 후보에는 건물 키와 `areaM2`. 건물별 및 구역 합계로 `availableAreaM2`, `effectiveModuleAreaM2`, `capacityKw`, `annualEnergyKwh`, `annualSunFraction`과 정렬 가능한 건물 요약. 유효 후보가 없으면 정상 0/빈 배열, 계산에 필요한 데이터가 없으면 null과 누락 근거를 반환한다. |

VWorld 키와 작업자 호출 자격 증명은 서버에 두고 브라우저에 전달하지 않는다. 계정·분석 이력 DB는 필요 없다. 비동기 작업 상태 및 결과는 비공개 작업 저장소에서 기본 24시간 동안만 유지하고, 요청 횟수·구역 및 타일 크기를 제한한다.

## 6. 추론 운영과 위험

웹과 API 중계는 Vercel에 둔다. 모델 학습 및 추론의 기본 환경은 학교 Backend.AI의 GPU 세션으로 계획한다. 실행 중인 Python 작업자가 대기열을 조회하고 결과를 기록한다. 활성 세션이 없으면 웹은 대기 상태를 표시한다. CPU는 소규모 구역의 대체 후보로 두고, P50/P95 대기·실행 시간과 최대 메모리를 측정해 서비스에 적용할지 결정한다. ONNX는 RTMDet 후처리 연산 호환성 및 좌표·마스크 동등성 검증 후 선택할 수 있다. GPU 가용성, 영상 이용 권한, 최소 해상도, 독립 권역 검증 결과가 확보되기 전에는 실운영 가능 또는 전국 실측 수준이라고 주장하지 않는다.

Task 1에서는 분석 계약이 문서에만 있다. 웹의 VWorld 지도 표시와 실제 건물 조회는 분석용 영상 처리·모델 추론과 연결하지 않았다. 모델 학습과 분석 연동은 이후 단계에서 검증한다.
